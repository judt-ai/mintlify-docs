title: "In-product agent"
description: "Build and change an App by chatting with the judt agent in the dashboard or through the sessions API."
---

Every App includes a built-in coding agent that you can chat with in the judt dashboard or drive programmatically through the Sessions API (`/api/apps/{id}/sessions`).

The in-product agent uses the same public [REST API](/manage/interfaces/api) as external agents: for each turn, judt mints a short-lived, App-scoped API token with your user identity and organization role.

## How the agent works

When you send a prompt in a session, judt creates a **turn** (`trn_...`) and executes an agent loop against the App's sandbox:

1. **Checkpoint**: Before the agent edits any files, judt commits any dirty changes in `/app` and records the starting commit in `turn.base_commit_id`. You can restore the App to `base_commit_id` at any time to undo the turn.
2. **Project memory (`AGENTS.md`)**: At the start of a turn, the agent reads `AGENTS.md` in `/app` (if present) and updates it as your App's architecture, routes, and database tables evolve.
3. **Preview verification**: After editing code, the agent calls `POST /api/apps/{id}/preview` to verify that `celld dev` builds and starts without errors before finishing its turn.
4. **Never publishes without instruction**: The agent commits its work in the sandbox, and only deploys to production (`POST /api/apps/{id}/deployments`) when you ask it to publish or when your organization role permits deployment.

## Models and reasoning effort

Call `GET /api/models` to list the models available for agent sessions:

| Model ID | Name | Supported `effort` levels |
| --- | --- | --- |
| `auto` (default) | Auto (selects Claude Sonnet 4.6) | `low`, `medium`, `high` (default), `max` |
| `anthropic/claude-sonnet-4-6` | Claude Sonnet 4.6 | `low`, `medium`, `high` (default), `max` |
| `anthropic/claude-opus-4-6` | Claude Opus 4.6 | `low`, `medium`, `high` (default), `max` |
| `anthropic/claude-haiku-4-5` | Claude Haiku 4.5 | Does not use `effort` (`supports_effort: false`) |

You can set `model` and `effort` when you create a session (`POST /api/apps/{id}/sessions`), update them on the session (`PATCH /api/apps/{id}/sessions/{session_id}`), or override them for a single turn (`POST /api/apps/{id}/sessions/{session_id}/turns`).

## Sessions and turns

### 1. Create a session

A session (`ses_...`) is a conversation thread on one App:

```bash
curl -X POST https://api.judt.ai/api/apps/$APP_ID/sessions \
  -H "Authorization: Bearer $JUDT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Add Stripe checkout",
    "model": "auto",
    "effort": "high"
  }'
```

If you omit `title`, the agent sets the session title automatically from your first turn.

### 2. Start a turn

Send a prompt (`1` to `32,000` characters) to `POST /api/apps/{id}/sessions/{session_id}/turns`:

```bash
curl -X POST https://api.judt.ai/api/apps/$APP_ID/sessions/$SESSION_ID/turns \
  -H "Authorization: Bearer $JUDT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "prompt": "Add a POST /api/checkout route that creates a Stripe Checkout session."
  }'
```

The API returns a `Turn` object (`201 Created`):

```json
{
  "id": "trn_7kL2mP9xQr4vW6nTc3YbZ8s",
  "session_id": "ses_2mK8pQ5xRtV9nW1sLc4ZbY7j",
  "app_id": "app_8fK2mQ7xRtV3nW9pLc4ZbY1s",
  "status": "running",
  "prompt": "Add a POST /api/checkout route that creates a Stripe Checkout session.",
  "model": "anthropic/claude-sonnet-4-6",
  "effort": "high",
  "base_commit_id": "cmt_3xK9mQ2pRtV7nW4sLc8ZbY5j",
  "input_request": null,
  "error": null,
  ...
}
```

### Turn statuses and concurrency

| Turn `status` | Meaning |
| --- | --- |
| `queued` | Waiting for an earlier turn in the same session to finish. Up to **5 turns** can be queued in a session. |
| `running` | Actively calling the model and running tools against the App. |
| `waiting` | Paused waiting for you to set requested Secrets (`turn.input_request`). |
| `completed` | Finished normally. |
| `failed` | Stopped due to an error (`turn.error` gives `code` and `message`). |
| `cancelled` | Stopped by `POST .../turns/{turn_id}/cancel` or `DELETE .../sessions/{session_id}`. |

Concurrency limits apply at the App and organization levels:

- **One active turn per App**: Only one session on an App can have a `running` or `waiting` turn at a time. Starting a turn in a different session on the same App returns `409 agent_busy`.
- **Queueing within a session**: Sending another turn to the **same** session while a turn is active places the new turn in `queued` status (up to 5 queued turns).
- **Organization limit**: Up to **3 turns** can run concurrently across all Apps in an organization (`429 org_turn_limit` if exceeded).

## Handle Secret requests (`waiting` turns)

When the agent needs an API key or credential, it requests the Secret by name and description. The turn enters `status: "waiting"` and sets `turn.input_request`:

```json
{
  "kind": "secrets",
  "message": "Provide your Stripe secret key so I can test the checkout route.",
  "secrets": [
    {
      "name": "STRIPE_SECRET_KEY",
      "description": "Stripe secret key (sk_test_... or sk_live_...)",
      "provided": false
    }
  ]
}
```

You have two options when a turn is `waiting`:

1. **Provide the Secrets**: Set each missing Secret using `PUT /api/apps/{id}/secrets/{name}` (or the Secret prompt card in the dashboard). Once all requested Secrets exist on the App, judt automatically resolves the request and resumes the turn.
2. **Decline the request**: Call `POST /api/apps/{id}/sessions/{session_id}/turns/{turn_id}/decline`. The turn resumes immediately and tells the agent to proceed without the Secret (for example, by leaving a placeholder or skipping live API tests).

## Cancel or undo a turn

- **Cancel a turn**: Call `POST /api/apps/{id}/sessions/{session_id}/turns/{turn_id}/cancel` to stop a `queued`, `running`, or `waiting` turn.
- **Undo a turn's file changes**: Read `base_commit_id` (`cmt_...`) from the turn object and call `POST /api/apps/{id}/restore` with `{"commit_id": "<base_commit_id>"}`.

## Read or stream session events

Every prompt, assistant message, reasoning block, tool call, and status change in a session is recorded as a `SessionEvent` (`sev_...`) at `/api/apps/{id}/sessions/{session_id}/events`.

### Fetch a JSON page

Send a standard `GET` request (with `Accept: application/json`) to read events in ascending order:

```bash
curl "https://api.judt.ai/api/apps/$APP_ID/sessions/$SESSION_ID/events?limit=100" \
  -H "Authorization: Bearer $JUDT_API_KEY"
```

Pass `?after=sev_...` with the last event `id` you received to fetch only newer events.

### Stream live events with Server-Sent Events (SSE)

Send `Accept: text/event-stream` to stream events in real time as the agent works:

```bash
curl -N https://api.judt.ai/api/apps/$APP_ID/sessions/$SESSION_ID/events \
  -H "Authorization: Bearer $JUDT_API_KEY" \
  -H "Accept: text/event-stream"
```

- Pass `Last-Event-ID: sev_...` (or `?after=sev_...`) to replay events after a specific event and then continue streaming live.
- Each SSE frame sets `id:` to the event's `sev_...` ID, `event:` to the event `type`, and `data:` to the JSON `SessionEvent` object.
- When all turns in the session settle (no turns are `queued` or `running`), the server sends `event: done` with `data: {}` and closes the stream.

### Session event types

| `type` | Payload in `data` |
| --- | --- |
| `user_message` | `{ "text": "..." }` — the user's prompt that started the turn. |
| `assistant_thinking` | `{ "text": "..." }` — the model's reasoning block. |
| `assistant_message` | `{ "text": "..." }` — the assistant's text reply. |
| `tool_call` | `{ "call_id", "tool", "title", "input", "output", "is_error" }` — an API tool call made by the agent (`output` is `null` while the tool is still running, then updated in place when it completes). |
| `input_requested` | `{ "kind": "secrets", "message", "secrets": [...] }` — the turn paused waiting for Secrets. |
| `input_resolved` | `{ "resolution": "provided" \| "declined" }` — the Secret request was satisfied or declined. |
| `turn_finished` | `{ "status": "completed" \| "failed" \| "cancelled", "usage"?, "error"? }` — the turn reached a final state. |
