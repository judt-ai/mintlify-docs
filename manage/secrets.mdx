title: "Secrets"
description: "Store credentials for an App outside its source."
---
Secrets store sensitive values—such as third-party API keys, webhook signing keys, and database credentials—outside your App's source files and Git history. Judt encrypts Secrets at rest and never returns their values in API responses, MCP tool outputs, or agent transcripts.

For non-secret configuration values that belong in version control, use the `vars` object in `wrangler.json` instead. See [Vars and Secrets](/build/vars-and-secrets).

## Naming and size rules

Every Secret belongs to one App and must follow these rules:

- **Name**: `1` to `128` characters matching `^[A-Z_][A-Z0-9_]{0,127}$`. Use uppercase ASCII letters (`A-Z`), digits (`0-9`), and underscores (`_`). A name cannot start with a digit.
- **Value**: Non-empty UTF-8 string up to `64 KiB` (`65,536` bytes).

If a Secret has the same name as a key in the `vars` object of `wrangler.json`, the Secret's value overrides the `vars` key at runtime.

## How Secrets reach your App

In your Worker code, read a Secret from the `env` argument passed to your handler (`env.SECRET_NAME`):

```javascript index.js
export default {
  async fetch(request, env) {
    const response = await fetch("https://api.stripe.com/v1/charges", {
      headers: {
        Authorization: `Bearer ${env.STRIPE_SECRET_KEY}`,
      },
    });
    return new Response(await response.text(), { status: response.status });
  },
};
```

Secrets are delivered differently to the development sandbox and to production:

| Environment | How Secrets are delivered | When changes take effect |
| --- | --- | --- |
| **Sandbox dev server (`celld dev`)** | Written to `/app/.dev.vars` when the sandbox starts. | On the **next sandbox start**. To apply a Secret change to a running sandbox immediately, call `POST /api/apps/{id}/stop` and then make your next sandbox request. |
| **Sandbox commands (`POST /command`)** | Injected as environment variables (`process.env.SECRET_NAME`) into the command process. | On the **next sandbox start** (or immediately if the sandbox was stopped when you set the Secret). |
| **Production deployment** | Injected into the deployed runtime configuration during `POST /api/apps/{id}/deployments`. Secrets are **not** available during `npm run build`. | On the **next deployment**. Changing a Secret does not alter an already-published deployment until you deploy again. |

## Manage Secrets with the API

Only organization `owner` and `admin` roles can create, update, or delete Secrets. Organization `member` roles can list Secret names and metadata.

### Create or update a Secret

You can set a Secret with `PUT /api/apps/{id}/secrets` (passing `name` and `value` in the body) or `PUT /api/apps/{id}/secrets/{secret}` (passing the Secret name or `sec_...` ID in the URL):

```bash
curl -X PUT https://api.judt.ai/api/apps/$APP_ID/secrets/STRIPE_SECRET_KEY \
  -H "Authorization: Bearer $JUDT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"value": "sk_live_51H..."}'
```

The API returns the Secret's metadata without its value:

```json
{
  "id": "sec_5mK9pQ2xRtV7nW3sLc8ZbY4j",
  "app_id": "app_8fK2mQ7xRtV3nW9pLc4ZbY1s",
  "name": "STRIPE_SECRET_KEY",
  "created_at": "2026-10-15T20:25:00.000Z",
  "updated_at": "2026-10-15T20:25:00.000Z"
}
```

### List or inspect Secrets

Call `GET /api/apps/{id}/secrets` to list all Secrets on an App, or `GET /api/apps/{id}/secrets/{secret}` (using either the `sec_...` ID or the Secret name, such as `STRIPE_SECRET_KEY`) to check whether a specific Secret exists.

### Delete a Secret

Call `DELETE /api/apps/{id}/secrets/{secret}` (by `sec_...` ID or Secret name):

```bash
curl -X DELETE https://api.judt.ai/api/apps/$APP_ID/secrets/STRIPE_SECRET_KEY \
  -H "Authorization: Bearer $JUDT_API_KEY"
```

After deleting a Secret, stop the sandbox (`POST /api/apps/{id}/stop`) to remove it from the sandbox environment, and create a new deployment (`POST /api/apps/{id}/deployments`) to remove it from production.

## Ask for Secrets from an MCP client

No tool on the [Judt MCP server](/connect-to-mcp) takes a Secret value. If a value is in a tool argument, it goes through the model provider's context window and the client's logs. The user types each value in the Judt dashboard instead.

### Ask the user to set Secrets

Call `request_secrets` with the names that the App needs and a one-sentence `reason`:

```json
{
  "app_id": "app_8fK2mQ7xRtV3nW9pLc4ZbY1s",
  "names": ["STRIPE_SECRET_KEY", "STRIPE_WEBHOOK_SECRET"],
  "reason": "Checkout charges cards with Stripe."
}
```

The result shows which names are set. While a name is missing, the result also has a `url`:

```json
{
  "secrets": [
    { "name": "STRIPE_SECRET_KEY", "provided": false },
    { "name": "STRIPE_WEBHOOK_SECRET", "provided": true }
  ],
  "url": "https://judt.ai/apps/app_8fK2mQ7xRtV3nW9pLc4ZbY1s?secrets=STRIPE_SECRET_KEY#secrets"
}
```

The `url` opens the App's Secrets page, with a password field for each missing name. The link holds only names. The user must sign in, and only the `owner` and `admin` roles can save the values.

- If the client supports URL elicitation (MCP revision `2026-07-28`), the client shows the page to the user. The tool call finishes after the user closes the page.
- If the client does not support URL elicitation, the agent gives the `url` to the user. Then it calls `request_secrets` again to make sure that each name is `provided`.

### Generate a Secret

For a value that no other service gives you, such as a session signing key, call `generate_secret` with `app_id` and `name`. Judt creates 32 random bytes, encodes them as base64url (43 characters), and stores them as the Secret. The agent never sees the value.

If a Secret with that name exists, `generate_secret` returns `409 secret_exists` and changes nothing. To replace the value, delete the Secret with `delete_secret` first.

### Delete a Secret

Call `delete_secret` with `app_id` and `name`.

## Provide Secrets to a waiting agent turn

When the [in-product agent](/platform-integrations#build-a-workflow-around-the-judt-agent) needs one or more Secrets to finish a task, its turn pauses with `status: "waiting"` and an `input_request` of `kind: "secrets"`:

```json
{
  "kind": "secrets",
  "message": "Set the Stripe API key so I can test the checkout endpoint.",
  "secrets": [
    {
      "name": "STRIPE_SECRET_KEY",
      "description": "Stripe secret key starting with sk_test_ or sk_live_",
      "provided": false
    }
  ]
}
```

As soon as you set every requested Secret (in the dashboard chat card or via `PUT /api/apps/{id}/secrets`), Judt automatically marks the request resolved and resumes the agent turn. From an MCP client, call `request_secrets` with the same names and give the user its `url`. If you do not want to provide the Secret, call `POST /api/apps/{id}/sessions/{session_id}/turns/{turn_id}/decline` so the agent continues without it.

<Warning>
  Do not put a real Secret value in a chat with a model. The model provider then sees it. Set the value in the Judt dashboard, or from a script with `PUT /api/apps/{id}/secrets/{name}` that reads the value from an environment variable or a file.
</Warning>
