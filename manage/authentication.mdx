Every request to the Judt REST API (`https://api.judt.ai/api`) and MCP server (`https://api.judt.ai/mcp`) requires an `Authorization` header.

| Path | Who it's for | Scope | How it starts |
| --- | --- | --- | --- |
| **API key** _(primary)_ | Scripts, CI, and agents | Organization-wide or a single App | Create a `judt_...` key in [API keys](https://judt.ai/api-keys) or mint a short-lived App token via `POST /api/tokens`. |
| **Agent OAuth** | Coding agents and MCP clients | Organization-wide (`apps:read`, `apps:write`) | Kicked off automatically via MCP OAuth or by following [`https://judt.ai/auth.md`](https://judt.ai/auth.md) against the OAuth endpoints. |

## 1. API keys (primary)

API keys are the primary way to authenticate scripts, CI jobs, and agents. An API key starts with `judt_` and is sent as a bearer token:

```http
Authorization: Bearer judt_...
```

- **Create in the dashboard**: Go to [API keys](https://judt.ai/api-keys) to create a key scoped to **All apps** in your organization or **one specific App**, with an optional expiration (`1 day` to `90 days`, or no expiration).
- **Mint short-lived App tokens via the API**: An organization-wide API key can call `POST /api/tokens` to mint a short-lived (`60s`–`24h`) token scoped to a single App—ideal for handing an agent or customer session isolated access to one App. See [Give an agent access to a single App](/manage/guides/agent-access).
- **Revoke anytime**: Revoke keys immediately from the [API keys](https://judt.ai/api-keys) page.

## 2. Agent OAuth

When an agent or MCP client authenticates with OAuth, you approve its access in your browser instead of copying a key. OAuth tokens act as you in the organization you select and carry `apps:read` and/or `apps:write` scopes.

There are two ways an agent kicks off OAuth:

- **Via the MCP server**: Connect an OAuth-capable MCP client (Claude Code, Cursor, VS Code, claude.ai, ChatGPT) to `https://api.judt.ai/mcp` without an `Authorization` header. An unauthenticated request returns `401` with a `WWW-Authenticate` header pointing to the RFC 9728 protected resource metadata (`/.well-known/oauth-protected-resource/mcp`), and the client opens your browser to sign in. See [Connect to MCP](/connect-to-mcp).
- **Via `auth.md` and the OAuth endpoints**: Standalone agents read [`https://judt.ai/auth.md`](https://judt.ai/auth.md) for step-by-step instructions. The agent discovers metadata at `https://judt.ai/.well-known/oauth-authorization-server`, registers dynamically (`POST /api/auth/oauth2/register`), starts the device authorization flow (`POST /api/auth/device/code`), and polls `POST /api/auth/oauth2/token` while you approve the code at `https://judt.ai/device`. Agents using the Personal Agent Protocol (Poppy) can also discover endpoints at `https://judt.ai/.well-known/poppy.json`.

You can view and revoke connected OAuth clients at any time on the [Connected agents](https://judt.ai/connected-agents) page, or an agent can revoke its own token at `POST /api/auth/oauth2/revoke`.

## Roles and other tokens

- **Organization roles**: Every API key and OAuth token inherits your role in the target organization. `owner` and `admin` can perform all actions (including creating/deleting Apps, managing Secrets, and deploying to production); `member` can read resources, edit sandbox files, run commands, commit, preview, and run agent turns, but receives `403 forbidden` on owner/admin actions.
- **App access tokens (for viewing private Apps)**: To let an automated caller or browser open a `password` or `private` published App (`https://<slug>.judt.dev`), mint a 5-minute access token with `POST /api/apps/{id}/access` and pass it in `X-Judt-Access-Token` or `?access_token=`. See [Previews and access](/manage/concepts/previews).

For general API conventions, OAuth scopes and lifetimes, DPoP key binding, and authentication error codes, see the [API reference](/api-reference/introduction).
